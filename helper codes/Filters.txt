Generic tools that can be specialized.

CRM → CRM for Plumbers.

Scheduler → Scheduler for Dentists.

You are right. Keyword matching is superficial and yields high "false positives."

To get **real business intelligence**, we need **derived metrics**—data points calculated by analyzing behavior, code structure, and community intent.

Here are **stronger, "Level 2" metrics** that are harder to calculate but much more accurate.

### 1. Identifying "Easy to Copy" (The Wrapper Detector)

Instead of just checking for "AI" keywords, we analyze the **Code-to-Dependency Ratio**.

* **Metric: The "Boilerplate Ratio"**
* **Logic:** If a project has 90% standard code (Next.js starters, Shadcn components) and only 10% unique logic, it is a wrapper.
* **How to measure:**
* **For Open Source:** Use a script (or LLM) to scan `package.json`. If main dependencies are just `openai` + `framework` and the `src/core` folder is small (<10 files), it is a wrapper.
* **For Closed Source:** Analyze the **feature release velocity**. If they ship "huge" features every 2 days, they are likely using off-the-shelf APIs for everything.




* **Metric: The "Commodity API" Dependency**
* **Logic:** Does the core value come from a commodity API (OpenAI, Replicate)?
* **How to measure:** Check if the product fails when the API is down (check status pages history vs product complaints). *Easier way:* Check their "Pricing" vs API costs. If their margin is thin (<20%), they are a reseller/wrapper.



### 2. Identifying "Tech Heavy" (The Moat)

True tech-heavy products have "proprietary complexity."

* **Metric: Commit "Churn" Complexity**
* **Logic:** Hard tech requires deep changes, not just UI tweaks.
* **How to measure:** Analyze GitHub commit history. Are changes concentrated in `README.md` / `components` (Low Tech) or `lib/algo`, `rust/core`, `c++/kernels` (High Tech)?
* **Signal:** Presence of low-level languages (Rust, C++, Go) in a web project often signals custom infrastructure.


* **Metric: Issue Resolution Time (Technical)**
* **Logic:** If bugs take weeks to fix and involve long technical discussions, the tech is complex.
* **How to measure:** Average time to close issues labeled "bug". Short time = trivial bug. Long time + many comments = complex engineering.



### 3. Identifying "Monetization Gap" (The Cash Cow)

Find products where users are *begging* to pay but can't.

* **Metric: The "Enterprise Request" Frequency**
* **Logic:** Users asking for "SSO", "SAML", "Invoicing", or "Team Seats" signals high willingness to pay.
* **How to measure:** Scrape GitHub Issues or Discord/Slack for keywords: "SSO", "Audit Log", "Compliance", "Procurement". Count these occurrences. High count + No "Enterprise" plan = **Gold Mine**.


* **Metric: "Self-Host" Fatigue**
* **Logic:** If a self-hosted tool is hard to install, people will pay for a managed version.
* **How to measure:** Count issues containing "Docker error", "Installation failed", "Config help". High failure rate = Opportunity for "Managed Hosting" (SaaS).



### 4. Identifying "Localization Opportunities" (The Geo-Gap)

Find products that are culturally locked but functionally universal.

* **Metric: Hardcoded Formats**
* **Logic:** Code that isn't ready for the world.
* **How to measure:** Scan the codebase (or UI) for hardcoded symbols (`$`), dates (`MM/DD/YYYY` - US only), or phone masks `(XXX) XXX-XXXX`.
* **Signal:** If a popular tool (10k+ stars) has these hardcoded, it is practically unusable in Europe/Asia. You can clone it, fix formats, and translate.


* **Metric: Regulatory Keywords**
* **Logic:** Products tied to specific US laws.
* **How to measure:** Presence of "IRS", "1099", "HIPAA" (US) without "GDPR" (EU) or "LGPD" (Brazil).

### Implementation: The "Deep Analysis" Workflow

You cannot do this for *every* product. You need a two-step funnel:

1. **Step 1 (Fast):** Use your existing filters (Votes, Category) to find the top 50 candidates.
2. **Step 2 (Deep):** Trigger an n8n workflow for these 50 that performs the "Deep Scan":

#### Example n8n "Deep Scan" Workflow:

1. **Input:** GitHub Repo URL.
2. **Node 1 (File Fetcher):** Fetch `package.json`, `Cargo.toml`, or `requirements.txt`.
3. **Node 2 (LLM Analysis):**
* *Prompt:* "Analyze these dependencies. Is the core logic proprietary or a wrapper around `openai`? Score from 0 (Wrapper) to 100 (Deep Tech)."


4. **Node 3 (Issue Scraper):** Fetch last 50 issue titles.
5. **Node 4 (LLM Sentiment):**
* *Prompt:* "Count how many users are asking for 'Pricing', 'Hosting', or 'Enterprise' features."


6. **Output:** Update your Product model with these new scores.

### Revised Database Model (To Store These Metrics)

We need to add a `Metrics` model to store these complex values.

```python
# Add this to products/models.py

class ProductAnalysis(models.Model):
    product = models.OneToOneField(Product, on_delete=models.CASCADE, related_name='analysis')
    
    # Scores (0-100)
    complexity_score = models.IntegerField(default=0)  # Low = Wrapper, High = Deep Tech
    commercial_intent_score = models.IntegerField(default=0)  # High = Users want to pay
    
    # Flags
    is_wrapper = models.BooleanField(default=False)
    has_enterprise_demand = models.BooleanField(default=False)
    is_us_centric = models.BooleanField(default=False) # Hardcoded $ or dates
    
    # Metadata
    analyzed_at = models.DateTimeField(auto_now=True)
    ai_summary = models.TextField(blank=True) # "Users complaining about Docker installation..."

```
